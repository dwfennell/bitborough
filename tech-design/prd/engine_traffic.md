# PRD: Engine — Traffic System

**System:** Traffic simulation
**Status:** Draft (future — Milestone 7)
**Parent:** `@bitborough/engine`

---

## Purpose

Traffic makes roads matter beyond simple connectivity. In the base game, roads are just a boolean requirement for zone development. The traffic system transforms them into a capacity problem: roads can become congested, and congestion has real consequences for growth and livability.

Traffic is the system that makes city *layout* matter — not just what you build, but where and how it connects.

---

## Design Goals

1. **Roads become a problem to solve, not just a checkbox.** Placing roads is easy; managing traffic flow is the challenge.
2. **Organic congestion.** Traffic jams should emerge naturally from residential-commercial-industrial commute patterns.
3. **Multiple solutions.** Players can solve traffic with more roads, better layout, mass transit, or mixed-use zoning.
4. **Visual feedback.** Congested roads should be visibly different from empty ones.

---

## Core Mechanics

### Traffic Generation

Traffic is generated by the need for residents to reach jobs and shops.

```
For each residential tile:
  Generate trips to:
  - Nearest employed industrial tile (commute to work)
  - Nearest commercial tile (shopping)

For each commercial tile:
  Generate trips to:
  - Nearest industrial tile (supply chain)
```

The number of trips scales with building density. A high-rise residential generates more traffic than a single house.

### Trip Routing

Each trip follows a road path from origin to destination, with a **maximum path length of 30 road tiles** (adapted from Micropolis's `MAX_TRAFFIC_DISTANCE = 30`). This limit is critical — it means distant zones need efficient road networks, not just any connection.

**Pathfinding:** Start with DFS (depth-first search) as Micropolis does — simpler to implement, and the 30-step limit keeps it fast. Can upgrade to A* later if more realistic routing is needed.

**Traffic density:** Each road tile traversed by a trip receives +50 traffic density (Micropolis convention). This accumulates across all trips, creating hotspots at bottleneck intersections.

**Route result categories:**
- Path found in ≤30 steps → success, normal zone behavior
- Path found but >30 steps → long commute penalty (slight demand reduction)
- Path dead-ends (no route to destination) → zone declines
- No road adjacent to zone → **immediate abandonment** (strongest penalty)

**Simplification:** Don't simulate individual vehicles. Calculate aggregate traffic load per road tile from all trip routes. Visual traffic (car sprites on roads) is a rendering concern scaled from the density number.

### Congestion

Each road tile has a capacity. When traffic load exceeds capacity, the tile is congested.

```
capacity per road tile: 100 trips
congestion = trafficLoad / capacity
  0.0 - 0.5: free-flowing
  0.5 - 0.8: moderate traffic
  0.8 - 1.0: heavy traffic
  > 1.0: gridlock
```

### Congestion Effects

| Congestion Level | Effect |
|-----------------|--------|
| Free-flowing (< 0.5) | No effect |
| Moderate (0.5 - 0.8) | Slight land value penalty (-5) |
| Heavy (0.8 - 1.0) | Land value penalty (-15), slows development |
| Gridlock (> 1.0) | Land value penalty (-30), demand suppression, buildings may decline |

Congested roads near residential zones reduce quality of life. Congestion near commercial zones reduces their attractiveness.

## Mass Transit (Future Enhancement)

Rail provides an alternative to roads for commuting. Residents near a rail line can "take the train" instead of driving, reducing road traffic.

```
If origin AND destination are within 3 tiles of a rail station:
  50% of trips use rail instead of road
  Rail has higher capacity per tile than road
```

This gives rail a clear gameplay purpose: it's expensive upfront but solves traffic problems that roads alone can't handle at scale.

## Traffic Density Map

The engine outputs traffic as a `Uint8Array` (0-255) in `GameState`:

```typescript
trafficDensity: Uint8Array  // per tile, 0 = no traffic, 255 = maximum gridlock
```

The game renders this as:
- Color-coded road tiles (green → yellow → red)
- Optional traffic overlay heatmap
- Vehicle sprite density on roads (visual only, not simulated individually)

## Performance Considerations

Traffic is the most computationally expensive system. For a city with thousands of residential tiles each generating multiple trips, pathfinding across the road network is O(trips × pathLength).

**Mitigations:**
- Run monthly (every 4 ticks), not every tick
- Use a pre-computed road graph (adjacency list), not tile-by-tile A*
- Cache route calculations, invalidate when road network changes
- For very large maps, sample trips (calculate 10% of trips, extrapolate)
- This is a prime candidate for Rust/WASM optimization if needed

## Interesting Decisions

1. **Grid vs. organic layout:** Grid layouts create many redundant paths (good for traffic). Organic layouts look nice but bottleneck at key intersections.
2. **Highway corridors:** Players will learn to create high-capacity arterial roads separating neighborhoods.
3. **Mixed-use zoning:** Placing commercial near residential reduces average trip distance and thus traffic.
4. **Rail timing:** Rail is expensive. Build it too early and you waste money. Build it too late and traffic gridlock stunts growth.
5. **Bulldoze and rebuild:** Sometimes the only fix for traffic is demolishing buildings to widen a road corridor — expensive and disruptive.

---

## Testing Strategy

- Verify traffic increases on roads between residential and commercial zones
- Verify congestion reduces land value
- Verify disconnected zones (no road path) generate zero traffic
- Verify adding a parallel road reduces congestion on the original
- Verify rail reduces road traffic when both endpoints are near stations
